# Early scam detection

Исследовательский проект по **раннему обнаружению мошенничества в диалогах** на русском, английском и китайском языках (RU / EN / ZH). В проекте исследуется не только вопрос «является ли диалог мошенническим?», но и **в какой реплике впервые появляется наблюдаемый обман**.

Репозиторий GitHub называется `early-scam-detection`; имя Python-пакета — `scam-onset`, имя для импорта — `scam_onset`.

> Это исследовательский код, а не готовый антифрод-сервис. Результаты на синтетическом корпусе нельзя напрямую переносить на реальные переписки. Репозиторий содержит отдельные исследовательские скрипты и ноутбуки, а не единую команду запуска всех экспериментов.

## Что изучает проект

У задачи три отдельных выхода:

| Выход | Значение |
|---|---|
| `is_scam` | Мошеннический ли диалог: `0` или `1` |
| `subtypes` | Набор подтипов: `phishing_link`, `money_request`, `other`; допустимы несколько одновременно |
| `onset` / `t*` | Номер первой реплики атакующей стороны с текстово наблюдаемым обманом; для немошеннического диалога — отсутствие значения |

**Онсет** — не обязательно просьба перевести деньги. Обман может начаться раньше: с ложной легенды, выдуманной угрозы или запроса конфиденциальных данных. Приветствие само по себе не является онсетом. Точные критерии заданы в руководствах по разметке, а не в примерах этого README.

Отдельно рассматриваются **hard negatives**: легитимные сообщения со ссылками, деньгами или предупреждениями, но без обмана. Наличие ссылки или денежного запроса само по себе не делает диалог мошенническим.

Основные направления работы:

- генерация и проверка многоязычного синтетического корпуса;
- разметка диалогов и оценка согласия аннотаторов;
- бинарная классификация, определение подтипов и момента начала обмана;
- оценка раннего обнаружения: качество предсказания и задержка сигнала;
- кросс-язычный перенос и эксперименты с ролью диалогового контекста.

## С чего начать

| Кому | Рекомендуемый маршрут |

| Студенту, впервые открывшему проект | Установить ядро → запустить тесты → выполнить демонстрационную калибровку → прочитать правила разметки |
| Аннотатору | Получить актуальные инструкции у сопровождающего проекта → пройти калибровку → получить подготовленный пак |

## Быстрый старт без GPU и API-ключей

Нужен **Python 3.10+**. Следующие команды рассчитаны на macOS / Linux; выполнять их нужно из корня репозитория.

```bash
git clone git@github.com:Lena05k/early-scam-detection.git
cd early-scam-detection

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"

python -m pytest tests/ -q
```

SSH-клонирование требует настроенного SSH-ключа GitHub. Вместо него можно использовать HTTPS: `https://github.com/Lena05k/early-scam-detection.git`.

В Windows PowerShell окружение активируется командой `.venv\Scripts\Activate.ps1`; команды `python -m ...` остаются теми же.

Ядро требует только `pyyaml` помимо стандартной библиотеки. Тесты генерации используют подставные ответы и не требуют платных запросов к LLM. Тесты лоссов и визуализаций пропускаются, если не установлены соответствующие необязательные библиотеки.

Скрипт `setup_project.sh` — исторический помощник для первоначальной раскладки файлов. **После обычного клонирования запускать его не нужно**: он в том числе перемещает файлы.

### Демонстрация калибровки

```bash
python scripts/run_iaa.py \
  --gold data/annotations/calibration_items_gold.csv \
  --annotations data/annotations/annotator_demo.csv
```

Это небольшой **синтетический пример для проверки инструмента**, а не результат разметки реального корпуса. Харнесс оценивает согласие меток и позиций онсета: Cohen κ, Krippendorff α, onset-MAE и agreement@±1.

Для сохранения результата добавьте `--save-json reports/iaa_demo.json`. Отрицательная α допустима и может означать систематическое расхождение аннотаторов.

### Необязательные зависимости

```bash
# Модели, обучение и ML-эксперименты
python -m pip install -e ".[ml,dev]"

# Графики
python -m pip install -e ".[viz,dev]"
```

ML-стек значительно тяжелее ядра. Установка `[ml]` не гарантирует наличие ускорителя: совместимость PyTorch с CUDA / MPS проверяется отдельно. Некоторые исследовательские скрипты требуют дополнительных библиотек, не перечисленных в extras; проверяйте их импорты и описание конкретного эксперимента.

## Структура репозитория

```text
configs/default.yaml           Общие параметры: языки, генерация, сплиты, лоссы, метрики
src/scam_onset/
  data/                        Генерация, сценарные группы, сплиты, HTML-паки разметки
  iaa/                         Согласие аннотаторов и калибровка
  losses/                      Функции потерь, включая PATL и штраф за задержку
  metrics/                     Метрики раннего обнаружения и OAD
  viz/                         Визуализация
  models/                      Пространство для моделей; пока только __init__.py
scripts/                       CLI-скрипты подготовки данных и экспериментов
tests/                         Автоматические тесты
notebooks/                     Исследовательские ноутбуки, в том числе для Kaggle
models/README.md               Реестр сохранённых моделей; сами веса не в Git
data/                          Локальные данные; основная часть не публикуется в Git
runs/                          Локальные результаты запусков; не в Git
reports/                       Сводные отчёты и генерируемые материалы
```

**Текущий код не ограничивается заглушками:** реализованы IAA-харнесс, генерация и валидация, групповые сплиты, инструмент разметки, метрики и лоссы. Обучение и анализ моделей находятся преимущественно в `scripts/` и `notebooks/`, а не в `src/scam_onset/models/`.

## Методология и правила разметки

Перед участием в разметке или воспроизведением экспериментов согласуйте с сопровождающим проекта актуальные определения меток и протокол работы. Если скрипт противоречит согласованному протоколу, сначала уточните расхождение.

### Важные исследовательские ограничения

- **Не смешивать silver и gold.** Silver — черновые метки генератора; gold — проверенная человеком разметка. Версию и происхождение меток нужно указывать в отчёте.
- **Не выбирать решения по тесту.** Архитектура, эпоха, пороги и гиперпараметры выбираются по `gold-dev`. `gold-test` используется только для итоговой оценки после фиксации решений.
- **Не переразбивать данные произвольно.** Используются групповые сплиты по `scenario_group`, чтобы связанные примеры не попадали одновременно в обучение и тест.
- **Не заглядывать в будущее при ранней детекции.** Предсказание на шаге `t` использует только префикс диалога до `t`. Классификация полного диалога — отдельный режим.
- **Сохранять режим разметки.** Просмотр всего диалога и последовательное раскрытие реплик не эквивалентны; поле `view_mode` важно для интерпретации онсета.
- **Учитывать артефакты синтетики.** Модель может выучить стиль генератора, а не признаки мошенничества. Высокая метрика сама по себе этого не исключает.

## Работа с данными и экспериментами

### Где взять данные

Публичный код и полная локальная исследовательская папка — не одно и то же. Корпуса, gold-разметка, приватные пакеты аннотаторов и веса **по умолчанию исключены из Git**. Клонирование не восстанавливает эти файлы.

Для воспроизведения обучения запросите у сопровождающего проекта разрешённый к использованию комплект данных. Вместе с ним нужны: версия корпуса, версия gold, маппинг сплитов, лицензия / условия использования и, желательно, контрольные суммы. **Публичная ссылка для скачивания полного комплекта пока не указана в этом README.**

Не заменяйте отсутствующий gold черновыми LLM-метками: такой запуск отвечает на другую исследовательскую задачу.

### Какие скрипты за что отвечают

| Этап | Точки входа |
|---|---|
| Генерация корпуса | `scripts/generate_corpus.py`, `scripts/generate_gen2.py` |
| Групповой сплит | `scripts/make_splits.py` |
| HTML-паки и проверка разметки | `scripts/make_annotation_pack.py`, `scripts/check_annotations.py` |
| Объединение и проверка меток | `scripts/merge_gold.py`, `scripts/verify_labels.py` |
| Калибровка | `scripts/run_iaa.py` |
| Классификаторы | `scripts/train_binary.py`, `scripts/train_tfidf.py`, `scripts/train_layer0.py`, `scripts/train_layer2.py` |
| Подтипы и онсет | `scripts/subtypes_eval.py`, `scripts/onset_eval.py` |
| Раннее обнаружение и перенос | `scripts/earliness_v2.py`, `scripts/crosslingual.py` |

Перед запуском CLI-скрипта смотрите его `--help` и пути по умолчанию. Исследовательские скрипты могут использовать исторические версии файлов или собственные параметры; `configs/default.yaml` не является универсальной конфигурацией для каждого запуска.

Например, `scripts/train_binary.py` ожидает по умолчанию:

```text
data/corpus/corpus_v1.jsonl
data/gold/gold_test_v1.csv
data/gold/gold_dev_split.json
```

Наличие более новой версии gold не означает, что скрипт автоматически её подхватит. Проверяйте аргументы `--corpus`, `--gold`, `--gold-dev` и протокол нужного эксперимента. Даже режим `--smoke` требует данных и может скачать предобученную модель; это не часть быстрого старта без данных.

### Генерация через API

Генерация выполняет платные внешние запросы. Для DeepSeek используется переменная окружения `DEEPSEEK_API_KEY`, для Anthropic — `ANTHROPIC_API_KEY`. Ключи не нужно записывать в Python-файлы, YAML, ноутбуки или README.

Проверяйте модели в конфигурации, объём генерации и пути вывода **до запуска**. Доступность конкретных моделей зависит от провайдера. Файл `.env` сам по себе не загружается автоматически генератором: ключ должен оказаться в окружении процесса. Не отправляйте приватные переписки внешнему API без разрешения.

### Как фиксировать результат эксперимента

В отчёте сохраняйте:

- команду запуска, commit кода и параметры;
- версии данных, gold и сплитов;
- seed, зависимости и используемое оборудование;
- критерий выбора модели по dev и зафиксированные пороги;
- итоговые метрики с указанием оценочного набора;
- ссылку на веса и способ их получения, если результат опирается на обученную модель.

Для итоговых моделей явно сохраняйте веса из временной среды Kaggle / Colab во внешнее хранилище. Реестр ведётся в [`models/README.md`](models/README.md); наличие метрик без сохранённых весов не обеспечивает воспроизводимость.

## Разработка и вклад в проект

1. Создайте отдельную ветку: `git switch -c feature/short-description`.
2. Найдите модуль в `src/scam_onset/` и связанный тест в `tests/`. Для учебного вклада удобно начать с теста на граничный случай, улучшения валидации или документации.
3. Меняя логику, добавьте или обновите тест. Не меняйте определения меток и формулы метрик без согласования методологии.
4. Выполните проверки:

   ```bash
   python -m pytest tests/ -q
   python -m ruff check src tests scripts
   ```

5. Перед коммитом просмотрите `git status --short` и `git diff --cached`. В pull request опишите изменение, проверки и ограничения.

Не добавляйте `torch` и тяжёлый ML-стек в калибровочный слой. Новые параметры по возможности выносите в конфигурацию или CLI, а не скрывайте в коде. Ноутбуки перед публикацией очищайте от выводов, ключей, персональных данных и локальных путей.

Makefile предоставляет сокращения `make install`, `make test`, `make iaa`, `make lint`, `make install-ml`. Прямые команды `python -m ...` удобнее, если `make` недоступен.

## Что публиковать в GitHub, а что оставлять локально

| Категория | Рекомендация |
|---|---|
| `src/`, `scripts/`, `tests/`, `pyproject.toml`, `Makefile` | Публиковать после проверки на секреты и локальные пути |
| `configs/` | Публиковать без ключей, приватных адресов и персональных данных |
| Калибровочный gold и `annotator_demo.csv` | Публиковать как небольшие синтетические примеры |
| Ноутбуки | Публиковать код, предварительно проверив и очистив выводы |
| Небольшие сводные отчёты | Публиковать выборочно после проверки содержимого; не путать с выгрузками отдельных диалогов |
| `.venv/`, кэши, `.DS_Store`, локальные настройки IDE / агентов | Не публиковать |
| API-ключи, `.env`, SSH-ключи, токены | Никогда не публиковать |
| Сырые переписки, основной корпус, gold и индивидуальная разметка | Не публиковать автоматически; нужен отдельный аудит прав, согласия и обезличивания |
| Пакеты аннотаторов, manifest-файлы, прогресс разметки | Оставлять локально: могут содержать тексты, заметки и служебное соответствие идентификаторов |
| `models/` с весами, `runs/`, checkpoints, TensorBoard | Хранить отдельно: Hugging Face Hub, объектное хранилище или согласованный архив; в Git — реестр и небольшие проверенные сводки |
| Рукописи `.docx`, временные материалы | Не публиковать автоматически; согласовать с автором |

Рабочие документы `.docx` исключены из Git и остаются локально.

### Проверка перед первым коммитом

```bash
# Сначала просмотреть список кандидатов, ничего не добавляя
git status --short
git add --dry-run .

# Проверить, что конкретный приватный файл игнорируется
git check-ignore -v .env

# После осознанного добавления выбранных файлов
git diff --cached --stat
git diff --cached
```

`.gitignore` не является проверкой безопасности и не скрывает уже отслеживаемые файлы. При утечке ключа недостаточно удалить файл: ключ нужно отозвать, а историю репозитория разбирать отдельно. Не используйте `git add -f` для обхода защитных правил без понимания последствий.
